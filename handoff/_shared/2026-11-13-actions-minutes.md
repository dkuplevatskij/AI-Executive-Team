## Задачи (по убыванию важности)

### GA-1. Не запускать Actions на правках одной документации — высоко
- **Что не так:** PR и слияние, где изменены только `CLAUDE.md`, `AGENTS.md` или `README.md`, запускают
  полный набор проверок, а в `ai-mentor`, `ai-recruit`, `nalog`, `onfive` — ещё и выкладку в прод.
- **Почему важно:** 14 PR с одной документацией 11.11.2026 потратили около 60 минут (оценка управляющего
  центра, не данные биллинга) и ничего не проверили.
- **Что сделать:** добавить `paths-ignore` в триггеры `pull_request` и `push`. В список входит только то,
  что не читает ни одна проверка, сборка и образ Docker. Кандидаты: `CLAUDE.md`, `AGENTS.md`, `README.md`,
  `docs/**`, `.claude/**` — каждый проверить по своему репозиторию. Известные исключения:
  - `DK`: часть `.md` участвует в `npm run check` (тексты телефона) — исключать только проверенное;
  - `claude-code-pro-trainer`: `src/raw/kit/*.md` и `sandbox/**` входят в сборку, не исключать; нужно лишь
    дописать `AGENTS.md` в существующие списки;
  - `ai-mentor`: после слияния одной документации коммит на сервере отстанет от `origin/main` —
    проверить, что `infra/deploy-remote.sh` и сверка коммита это переносят, иначе написать собственнику.
- **Не делать:** если в настройках ветки проверка отмечена обязательной (required status check), фильтр
  оставит PR с одной документацией навсегда «ждущим». Узнать это у собственника до правки; если так —
  фильтр не ставить и сообщить.
- **Готово, когда:** PR только с файлами из списка не создаёт запусков; PR с кодом создаёт те же, что раньше.

### GA-2. Таймауты у задач и у шагов со скачиванием — высоко
- **Что не так:** без `timeout-minutes` зависшая задача идёт до предела GitHub в 6 часов. 11.11.2026 шаги
  установки пакетов в `LogisDoc-Pro` и Chromium в `agent-trainer` висели по 10 минут, дважды каждый.
- **Почему важно:** одно зависание способно съесть заметную часть месячного лимита (2000 минут).
- **Что сделать:** каждой задаче без таймаута поставить `timeout-minutes` — примерно вдвое больше обычной
  длительности по последним зелёным запускам (смотреть в истории Actions, числа не угадывать). Шагам,
  которые качают из сети (`apt-get`, `playwright install`), — свой таймаут на шаг.
- **Готово, когда:** у каждой задачи в файлах из таблицы есть `timeout-minutes`; в PR перечислены значения
  и длительности, от которых они взяты.

### GA-3. Отмена устаревших запусков проверок — средне
- **Что не так:** новый push в ту же ветку не останавливает проверку предыдущего коммита.
- **Что сделать:** блок `concurrency` на уровне workflow проверок с `cancel-in-progress: true` для
  запусков по PR. Ограничения:
  - выкладки не отменять никогда: у них очередь (`cancel-in-progress: false`), её не менять;
  - `nalog/deploy.yml`: очереди нет вообще, две выкладки могут идти одновременно — добавить очередь
    (`group: deploy-production`, `cancel-in-progress: false`);
  - `LogisDoc-Pro/ci.yml`: тот же файл запускается кнопкой и ведёт к выкладке — отмена только для
    события `pull_request`, запуск с `main` и с кнопки не отменять;
  - `ai-recruit/checks.yml`: его же вызывает `deploy.yml` через `workflow_call` — запуск из выкладки
    не отменять.
- **Готово, когда:** второй push в PR отменяет запуск первого; запуски выкладки не отменяются.

## Проверка (общая для всех задач)
- До 01.12.2026 минут нет: запуски падают за секунды, проверить поведение в Actions нельзя. Синтаксис
  проверить локально (`actionlint`, если ставится; иначе — разбором YAML) и написать, чем проверено.
- После 01.12.2026: PR с одной документацией — запусков нет; PR с кодом — запуск есть и зелёный;
  второй push отменяет первый запуск. До этой проверки в отчёте писать «не проверено в Actions».

- Меньше задач на запуск: в `DK` их 7, в `LogisDoc-Pro` 5, каждая округляется до минуты вверх.

- Свой раннер или покупка минут.
